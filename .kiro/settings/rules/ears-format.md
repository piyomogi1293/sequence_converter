# EARS形式ガイドライン

## EARS（Easy Approach to Requirements Syntax）とは

システム要件を明確かつ曖昧さなく記述するための構造化された構文。受け入れ基準の記述に最適。

## 基本パターン

### 1. Ubiquitous（普遍的）

常に真である要件：

``` bash
<主語> は <動作> しなければならない
```

**例**:

- `SequenceConverter は PNG形式の画像を受け入れなければならない`

### 2. Event-driven（イベント駆動）

特定のイベントによってトリガーされる要件：

``` bash
<トリガー条件> とき、<主語> は <動作> しなければならない
```

**例**:

- `ユーザーが画像ファイルを提供したとき、SequenceConverter はファイルを受け入れて処理を開始しなければならない`

### 3. State-driven（状態駆動）

特定の状態にある間の要件：

``` bash
<状態条件> の間、<主語> は <動作> しなければならない
```

**例**:

- `画像処理が進行中の間、SequenceConverter は進捗情報をログに記録しなければならない`

### 4. Unwanted behavior（望ましくない動作）

避けるべき動作：

``` bash
<トリガー条件> とき、<主語> は <望ましくない動作> してはならない
```

**例**:

- `無効な画像形式を検出したとき、SequenceConverter は処理を続行してはならない`

### 5. Optional（オプション）

条件付きで実行される要件：

``` bash
<条件> の場合、<主語> は <動作> しなければならない
```

**例**:

- `テキスト色が赤の場合、SequenceConverter は [#red] 構文を含めなければならない`

## 受け入れ基準での使用ガイドライン

1. **主語の選択**:
   - ソフトウェアシステムの場合：システム名/サービス名を使用
   - ハードウェアの場合：デバイス名を使用
   - 例：`SequenceConverter`, `Sequence_Diagram_Converter`

2. **動作の明確性**:
   - 具体的で測定可能な動作を記述
   - 曖昧な表現（「適切に」「正しく」等）は避け、具体的な基準を示す

3. **条件の明示**:
   - トリガーとなる条件を明確に記述
   - 複数の条件がある場合は分割して記述

4. **検証可能性**:
   - テストで検証できる形式で記述
   - 主観的な判断が入らないようにする

## アンチパターン

避けるべき記述：

- ❌ `システムは高速に動作する`（測定不可能）
- ✅ `システムは 1000×1000 ピクセルの画像を 3秒以内に処理しなければならない`

- ❌ `システムは適切にエラー処理を行う`（曖昧）
- ✅ `入力ファイルが破損しているとき、システムはエラーメッセージを表示してユーザーに通知しなければならない`
